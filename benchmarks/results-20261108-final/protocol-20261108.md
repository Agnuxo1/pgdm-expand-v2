## Detailed Implementation Plan

For a source interval I, a join match r.key = s.raw_id implies r.key is in I. Filtering r by I therefore preserves both matching rows and unmatched source rows of an INNER/LEFT join. Only previously proven row-wise destinations in the same segment are eligible. Other joins and unsupported identifier syntax retain their original SQL. The official generator, seeds, recipe files, validation calls and version/dump handling remain unchanged. Engine version increments so old job SQL is not silently mixed with a new plan.

Use the existing PostgreSQL 16 Docker image and official deterministic data, 4 vCPU, 6 GiB, one active data-volume owner, queued CPU job. Source snapshots and file hashes accompany the logs. No Kaggle or local GPU.

1. Run the Python unit suite, including independent parser/adversarial cases.
2. Smoke: 100k, control and H1, verify natural-key content, counters and exactly one version/dependency per destination.
3. Exploratory screen: 1M, alternating control/H1. Preserve every run including failures. Inspect statement timing to identify remaining cost.
4. Confirmation: at least 3 alternating paired repetitions at 1M and 3M for a promising candidate; report individual times, mean, sample SD and paired geometric speed-up. Flag machine contention. Historical bench A/B are separate series.
5. Selection, fixed before confirmation: for paired time ratios r_i = T_control_i / T_candidate_i, report geometric mean G = exp(mean(log(r_i))). Require G >= 1.10 at 1M or 3M, all three paired ratios > 1 at that size, G >= 0.98 and no paired ratio < 0.95 at the other size. Require exact content/counter/version checks on every run, candidate maximum PSS <= 1.10 times control maximum PSS at each size, and temporary bytes <= control maximum (no source materialization). A failed run is an acceptance failure, never silently dropped. If resource admission or another workload causes a documented infrastructure failure, retain that attempt, rerun the entire affected pair and label both. Do not discard timing outliers post hoc.
6. Recovery: Manager/SSH loss, killed runner/workers and immediate PostgreSQL restart; compare with control digests, verify committed chunk reuse, counters and idempotent versions. Add source-change, global-only and cancellation tests.
7. One scoped fresh-context Elephant/Goldfish review of the final design and evidence, followed by executable checks for serious findings. Record scope and unfinished review work accurately.

## H3 addition before any H3 timing

H3 fuses `qualified.column -> 'object_key' ->> 'field_key'` into `qualified.column #>> ARRAY['object_key','field_key']`. This avoids building the intermediate JSONB object. Eligibility is restricted to simple unquoted qualified columns and constant nonnumeric identifier-like keys; other syntax remains unchanged. No dataset content is inspected by the optimizer. Unit coverage must include comments/dollar literals, numeric-key rejection, idempotent rewriting and separate job identities. A PostgreSQL property check compares both expressions over SQL NULL, JSON null, missing keys, scalar values, arrays and objects. Benchmark arms are H1-only, H3-only and combined; original recipes/generator remain untouched. The same predeclared confirmation criteria apply. Exploratory arm selection and all negative results must be disclosed.

Infrastructure amendment before new timings: the server CPU queue is blocked by an idle GPU campaign. The documented CPU bridge is used for a Docker benchmark limited to 4 cores and 6 GiB, without modifying that campaign. Its first run uses the existing 1M official dataset; 100k smoke will be retained as a separate later regression check. The discarded WSL driver received SIGHUP after generation and produced no timing observations.

## Bounded H4 screen, recorded before measurement

While H3 confirmation continues on the server, screen one optional extraction prototype on the separate workstation CPU/WSL, with no GPU. H4 uses one lateral jsonb_to_record per source row for frequently used object fields, all declared text, and CASE maps non-objects to SQL NULL. It rejects existing LATERAL/NATURAL syntax and top-level wildcard projections, uses collision-checked synthetic output names, and preserves casts/escaped-key guards. It remains disabled by default and is not part of the H3 confirmation snapshot.

First require exact bag equality for 1007 synthetic JSON/scalar/NULL rows, including a source column whose unqualified name equals a JSON field. Then run three AB/BA/AB extraction-only micro pairs over the same first 50k official source rows with PostgreSQL parallel query disabled. This is a microbenchmark, not MEASURED PROCESSING TOTAL. Promote to a full engine experiment only if geometric extraction speed-up over H3 is at least 1.30 with every pair faster. Otherwise retain the negative/prototype artifact and remove it from the deliverable. A promoted candidate still requires the full original confirmation/resource/recovery criteria and independent review. Never pool WSL micro timings with server benchmarks.

## H5 bounded filter-pushdown screen, before timing

H5 rewrites one CROSS JOIN LATERAL VALUES constructor into a UNION ALL of SELECT branches, preserving every expression and the original output alias. Eligibility requires homogeneous rows: a typed constant smallint followed solely by complete, uncast source JSON text extraction expressions. Same columns, types and row multiset; no new source data or computed answers. The hypothesis is that PostgreSQL can push the position/weight/type predicates into each SELECT and avoid extracting fields from rejected positions. The official SQL files and versioned recipes stay untouched.

First require exact bag equality on the first 1000 generated source rows in an extraction-only model. Then screen three counterbalanced micro pairs at 50k rows, no parallel query, H3 vs H3+H5. The model omits the parent lookup/surrogate id solely to isolate transformation cost; it is not an official benchmark. Promote only if geometric micro speed-up >=1.30 and every pair is faster. If promoted, implement the guarded compiler in the actual engine and require full MEASURED PROCESSING TOTAL, all integrity/resources/recovery checks and independent review before selection. Preserve failed screens.
